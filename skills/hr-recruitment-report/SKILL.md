# Recruitment Report Skill 招聘汇报生成

## 适用场景

当用户要求生成招聘报告、候选池汇报、招聘漏斗分析、周报、月报、季报、年终招聘总结、PPT 汇报页内容时使用本 Skill。

本 Skill 负责把安全数据和业务判断组织成 HR 可汇报的页面内容。HR MCP/API 后端不生成报告，只提供安全候选人数据、事实统计和结果保存能力。

## 核心定位

招聘报告不是普通文章，也不是把字段结果堆成 Markdown。HR 更常需要的是可放进 PPT 或飞书文档的汇报页：

- 一页讲清楚招聘漏斗、转化率、流失原因和关键瓶颈。
- 一页讲清楚候选池结构、岗位供给缺口和来源质量。
- 一页讲清楚本周期关键指标卡、风险判断和行动建议。
- 一页讲清楚重点岗位或重点候选人推进状态。

不要只输出通用 Markdown 章节。默认输出应是“页面标题 + 核心结论 + 指标/图表数据 + 业务解读 + 行动建议”的 PPT 型结构。

## 可生成的报告页类型

### 1. 招聘漏斗分析页

适合问题：

- “生成一份芯片建模工程师招聘漏斗报告。”
- “看一下应用软件开发工程师从投递到入职哪里流失最多。”
- “这个岗位招聘过程卡在哪一步？”

推荐页面结构：

```text
页面标题：高端人才招聘漏斗分析
核心结论：一句话说明当前最大流失点和优先动作。
漏斗指标：
  - 简历投递
  - 初筛合格
  - 初步通过
  - 终面通过
  - 成功入职
转化率：
  - 初筛通过率
  - 初面/技术面通过率
  - 终面通过率
  - Offer/入职转化率
流失原因：
  - 来源质量不足
  - 岗位要求与履历不匹配
  - 关键技能证据不足
  - 面试节奏或候选人意愿风险
图表建议：
  - 主图：漏斗图
  - 辅图：各阶段转化率条形图
  - 右侧：问题诊断和行动建议
```

如果后端当前事实数据没有完整阶段字段，必须说明“当前数据只能覆盖可见状态字段”，不要编造漏斗阶段人数。

### 2. 候选池结构分析页

适合问题：

- “生成应用软件开发工程师候选人池分析报告。”
- “这个岗位候选人供给怎么样？”
- “候选池质量和风险有哪些？”

推荐页面结构：

```text
页面标题：候选池结构与供给质量分析
关键指标卡：
  - 候选人总量
  - 在流程人数
  - 高匹配样本人数
  - 重点风险人数
结构拆解：
  - 状态分布
  - 来源分布
  - 工作年限分布
  - 学历/学校/专业分布
  - 技能栈覆盖
图表建议：
  - 环形图：来源或状态占比
  - 条形图：岗位/技能/工作年限分布
  - 表格：样本候选人证据
业务解读：
  - 供给是否充足
  - 结构是否偏科
  - 哪些证据支撑候选池质量
  - 哪些风险需要面试或补充数据验证
```

### 3. 周报/月报/季报页

适合问题：

- “生成本周招聘进展汇报。”
- “出一份月度招聘数据汇报。”
- “帮我做季度招聘复盘。”

推荐页面结构：

```text
页面标题：招聘周期进展汇报
关键指标卡：
  - 新增候选人
  - 当前流程中候选人
  - 淘汰候选人
  - 拟入职候选人
  - 重点岗位缺口
图表建议：
  - 趋势折线图：按创建时间或更新时间统计
  - 堆叠条形图：岗位 x 状态
  - 环形图：来源结构
业务解读：
  - 本周期主要进展
  - 流程积压点
  - 高风险岗位
  - 下周期行动建议
```

如果数据库缺少明确时间范围统计能力，报告必须说明数据口径，并基于 `create_time`、`update_time` 或当前可用事实进行保守分析。

### 4. 重点岗位汇报页

适合问题：

- “给我一页 AI芯片工程师招聘汇报。”
- “重点讲一下后端工程师岗位现在有没有合适人选。”

推荐页面结构：

```text
页面标题：重点岗位招聘推进页
标准来源：岗位 Markdown 标准路径
候选人概览：
  - 推荐
  - 待确认
  - 不推荐
样本证据：
  - candidate_id
  - 匹配证据
  - 风险点
  - 面试验证建议
行动建议：
  - 继续推进的人
  - 需要补充确认的问题
  - 需要扩大召回的方向
```

如果报告中包含推荐候选人，必须遵循 `skills/hr-candidate-screening/SKILL.md` 的推荐逻辑。

如果报告涉及“可推荐候选池”，必须拆成：

- `active` 主池：仍在招聘流程中的优先推进人群。
- `old_rejected` 补充池：`status=REJECTED` 且 `update_time` 超过 180 天、需要由筛选 Skill 判断是否高度匹配的人群。
- `recent_rejected` 不推荐池：近期被拒候选人，只能用于风险、流失或流程诊断。
- `hired` 历史成功池：已入职候选人，只用于供给画像、转化或成功样本分析。

不要把大量 `REJECTED` 候选人当作同等可推进人群；报告必须说明 `update_time` 在 `REJECTED` 状态下作为被拒时间使用。

## 数据工具调用方式

1. 用 `query_talent_pool_facts` 获取 count、岗位分布、状态分布、来源分布等事实。
2. 用 `search_candidate_safe_profiles` 获取安全候选人样本。
3. 必要时用 `get_candidate_safe_detail_batch` 补充安全详情。
4. 不调用不存在的后端报告生成工具。
5. 不把联系方式写入报告。

## 输出规范

报告输出应优先按 PPT 页面组织，而不是普通长文：

```text
第 1 页｜标题
核心结论
关键指标卡
图表建议
数据表
业务解读
行动建议
数据口径与限制
```

每页必须包含：

- 可直接作为页标题的标题。
- 一句话核心结论。
- 可视化建议，例如漏斗图、环形图、条形图、趋势图或矩阵表。
- 指标数据和计算口径。
- HR 可执行的行动建议。

## 边界

- 不生成自由 SQL。
- 不编造数据库没有返回的阶段人数、转化率或趋势。
- 不输出联系方式字段。
- 不把薪酬、绩效、考勤、培训等外部 HR 系统内容写成事实；如果用户要完整人力资源年终总结，只能说明 P0 当前只接入招聘人才库数据。
- 没有 Markdown 岗位标准的岗位，可以生成事实性招聘数据页，但不能生成推荐结论。
